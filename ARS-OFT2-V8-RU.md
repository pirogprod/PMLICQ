# PMLICQ V8 — защита работающего ARS и экспериментальная отправка крупных файлов

Основа: V7, без замены принимающего ARS-кода (`server.cpp`) и без изменений X-статусов.

## Что показал присланный Netlib-лог

* Малые файлы ~3.2 и ~3.3 MB завершились успешно (OFT2 stage=5).
* При отправке 67,573,610 B удалённая сторона отправила rendezvous type=1 (CANCEL); последовал обрыв соединения WSA 10054 после 2,621,440 B.
* При отправке 15,232,562 B то же самое произошло после 6,422,528 B.
* Оба случая были в OFT2 stage=3 (DATA), а не ALLOCATE, READY либо DONE.
* Это НЕ доказывает причину отмены; скорость передачи — гипотеза для проверяемого обхода.

## V8

1. Только для исходящих ARS-передач размером >= 8 MiB включено ограничение скорости по умолчанию **1024 KiB/s**. Для меньших файлов функционально сохранён старый код передачи.
2. DBEditor++: DWORD `ArsUploadKiBps` в модуле аккаунта PMLICQ. `1024` по умолчанию, `512` — тест более медленного режима, `0` — без ограничения, как в V7. Никаких изменений UI настроек.
3. Ограничение применяется только в sender callback; структура OSCAR/ARS/OFT2-пакетов, ALLOCATE, READY и приём не изменены. Задержка до 250 ms на блок, может повлиять на время передачи.
4. В прямом OFT2 и direct fallback внутренний TLV IP теперь содержит адрес локального интерфейса, а не копию внешнего IPv4. Внешний IP по-прежнему задаётся `Oft2ExternalIP` при NAT; реальное подключение требует `Oft2ListenPort` и проброс TCP на роутере. Само по себе изменение TLV не решает NAT.
5. Расширен диагностический вывод исходящего ARS: скорость, полный результат, стадия, флаг отмены.

## Как проверять

1. Сохранить рабочую V7 DLL и БД Miranda.
2. Собрать V8; проверить 3 MB (регрессия), 15 MB, 60 MB.
3. Если происходит отмена/10054, повторить для `ArsUploadKiBps=512` и передать Netlib-лог; если ошибка возникает и медленно, нужна диагностика веб-клиента Mandarin и проверка OFT2 метаданных/контрольных сумм.
4. Прямой OFT2 испытывать отдельно только с реально достижимым публичным IP и проброшенным портом.
